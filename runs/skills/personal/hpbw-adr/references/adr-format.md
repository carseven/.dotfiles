# ADR format and validation

HPBW ADRs live in `aec_documentation` (Docusaurus). Start from the newest ones as the style reference, and quote the repository's own conventions over this summary when they differ (`git log --diff-filter=A --name-only -- docs/ADRs | head`).

## Location and name

- `docs/ADRs/<YYYY>-Q<n>/<YYYY-MM> <Title>.md`, for example `docs/ADRs/2026-Q4/2026-11 File processing state.md`. The SitePrint team uses `docs/ADRs/SitePrint/<YYYY-MM-DD> <Title>.md`.
- No ADR number and no front matter. The sidebar is autogenerated.
- Related-document links use relative paths for `.md` files, and absolute `https://github.azc.ext.hp.com/bcn-robotics/aec_documentation/blob/main/<path>` URLs for YAML, JSON and other files.

## Sections

```markdown
# <Title>

## Status
| | |
| --- | --- |
| **Document Status** | Proposed |
| **Authors** | <email> |
| **Team** | <team> |
| **Created** | <Month YYYY> |
| **JIRA** | [LFPSW-n](https://hp-jira.external.hp.com/browse/LFPSW-n) <title> |
| **Related** | <related Jira, ADRs, specs, Figma> |
```

1. **Summary**: what we decide, in a few sentences.
2. **Context**: how it works today (a sequence diagram), what is wrong, the requirements with their source identifiers, and "Facts that shape the design". Each fact carries evidence.
3. **Decision**: numbered sub-decisions, each with a table, a state or sequence diagram, or a SQL and API sketch. Include the data model, the owner of each change, the API contract, events, client behaviour, the feature flag and the rollout order.
4. **Edge cases**: a table of case and behaviour. Cover duplicate and out-of-order events, retries, partial failure, timeouts, versions, concurrent users, abandoned flows and old clients.
5. **Options considered**: a table of option and why not.
6. **Consequences**: Good, and Costs and risks.
7. **Out of scope and open questions**: numbered. State what would settle each one.
8. **Implementation plan**: one row per repository with its change, then the tests.

Writing rules:

- Plain words, short sentences, the same word for the same thing. Say "the file" or "the service", and name the service.
- Facts and decisions stay apart. A fact has evidence. A decision has the alternatives it beat.
- When a fact comes from a deployed environment, say which one.
- Correct an older ADR's claim when the code disagrees, and say so in the text.
- Leave secrets, presigned URLs, tokens and personal data out.

## MDX safety

Docusaurus parses `.md` as MDX. Outside code spans and fences, `<`, `>`, `{` and `}` break the build. Write `projects/<projectId>` inside backticks.

## Contract changes

When a decision changes a REST endpoint or an event, change the contract in the same branch:

- OpenAPI sources: `API/aec_api/components/` and `API/aec_api/paths/`. The `*_merged.yml` files are generated and untracked.
- AsyncAPI: `ASYNCAPI/aec/*.yml`.
- Product guides: `docs/Product technical docs/`.

## Validate

Run from the `aec_documentation` root. The packages are in its `node_modules`.

```bash
# Mermaid blocks of the ADR
node --input-type=module -e "
import fs from 'fs';
import { JSDOM } from 'jsdom';
const dom = new JSDOM('<!DOCTYPE html><body></body>');
globalThis.window = dom.window; globalThis.document = dom.window.document;
const mermaid = (await import('mermaid')).default;
const md = fs.readFileSync(process.argv[1], 'utf8');
const blocks = [...md.matchAll(/\`\`\`mermaid\n([\s\S]*?)\`\`\`/g)].map((m) => m[1]);
for (const [i, b] of blocks.entries()) { await mermaid.parse(b); console.log('mermaid block', i, 'ok'); }
" "docs/ADRs/<folder>/<file>.md"

# An AsyncAPI file
node --input-type=module -e "
import fs from 'fs';
import { Parser } from '@asyncapi/parser';
const { document, diagnostics } = await new Parser().parse(fs.readFileSync(process.argv[1], 'utf8'));
console.log('asyncapi valid:', !!document, diagnostics.filter((d) => d.severity === 0).map((d) => d.message));
" ASYNCAPI/aec/<file>.yml

# The OpenAPI merge resolves every reference
node ymlConverter ./API/aec_api/aec_api.yml /tmp/aec_api_merged_check.yml && rm /tmp/aec_api_merged_check.yml
```

Parse each changed YAML file with `js-yaml`. Search the ADR for raw `<` or `{` outside code. State in the hand-off which checks ran. The full `npm run build` is slow, so run it only on request.

## Git and pull request

- Branch `LFPSW-<n>-<slug>` from `origin/main`. Commit message `[LFPSW-<n>] ADR: <title>`, with a body that lists the contract changes and the trailer `Co-authored-by: Copilot <223556219+Copilot@users.noreply.github.com>`.
- Pull request only on request. Title `[LFPSW-<n>] ADR: <title>`, base `main`. Use `.github/PULL_REQUEST_TEMPLATE.md`: keep its `## Description` heading and its closing `Fixes [LFPSW-n](...)` line. Put the summary tree or diagram, the decisions to review, the evidence of the checks that ran, and the merge danger inside Description.
